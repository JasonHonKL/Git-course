    一句话模型

    Git 是一个内容寻址的对象库（不可变，按内容哈希取名），加一层可变的引用（分支、HEAD、reflog），中间用索引把工作区与下一次提交连接起来。后面每一节都在展开这句话里的一个词。

    模块 1 · 小节 1

    一次 commit，磁盘上多了什么？

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    在一个只有两个文件的仓库里提交一次，然后问 Git 要它的原始内容：

    $ git log -1 --oneline
a1b2c3d add hello.txt
$ git cat-file -p HEAD
tree 07ed5a7aebb914e3a02edf6d622b82d364037e3c
parent 9fceb02d0ae598e95dc970b74767f19372d61af8
author A U Thor <a@example.com> 1767225600 +0000
committer A U Thor <a@example.com> 1767225600 +0000

add hello.txt

    注意最后一段：git cat-file -p 把对象解压后原样打印出来。commit 不是什么二进制黑盒，它是一段带头的纯文本。文件内容不在里面，只有一个 tree 的哈希。

    第一次见这些词：blob 存内容，tree 存目录结构。

    对象的“名字”是内容哈希：同样的字节永远得到同样的名字，改一个字节就得到一个全新的对象。引用则相反，它只是一个文件，里面写着一行十六进制；移动分支，就是改写这一行。

    这也解释了一个常见困惑：git commit --amend 并没有改掉旧提交。它造了一个新对象，然后把分支引用指过去；旧对象还在，直到 gc 发现没人引用它。

    预测只改提交信息（git commit --amend -m "new"），commit 的哈希会怎样？

    commit 对象的解剖

    这四行头加一个空行加正文，就是 commit 的全部。父提交可以没有（根提交），也可以不止一个（合并提交）。

    所以“提交”不是把文件打包上传，而是给一棵已经存在的目录树签个名。树和文件对象可能早就写好了；提交只是把树、父提交、作者和时间绑在一起。

    术语

    对象是不可变的内容；引用是可变的指针；索引是两者之间的待提交快照。

    对象按内容哈希命名，所以任何改动都会产生一个新对象，旧对象不会被覆盖；分支只是一个写着哈希的文件，移动分支就是改写这个指针。执行 amend 时，Git 用新的 tree、parent 和提交信息写出一个新的 commit 对象，然后把当前分支引用从旧哈希改到新哈希。旧提交仍然存在，只是不再被这个分支引用，最终可能被 gc 回收。因此“不可变”约束的是对象层，“可移动”描述的是引用层。

    • 对象不可变，分支/HEAD 可变；历史操作大多是“造新对象 + 移引用”。

    命令是怎么被接住的？

    阅读 ≈6 分钟 · 检查 ≈4 分钟

    你已经知道提交留下了什么。现在反过来问：git commit 这行字，是怎么变成一个 C 函数的？答案在 git.c 的一张表里。

    表长这样

    git.c:533
    static struct cmd_struct commands[] = {
	{ "add", cmd_add, RUN_SETUP | NEED_WORK_TREE },
	{ "am", cmd_am, RUN_SETUP | NEED_WORK_TREE },
	...
	{ "commit", cmd_commit, RUN_SETUP | NEED_WORK_TREE },
	...

    三个字段：命令名、函数指针、启动选项。选项决定“调用实现之前，主程序要替它做多少准备工作”。

    RUN_SETUP | NEED_WORK_TREE

    RUN_SETUP：必须找到仓库；找到后切换到工作树根，并把用户原来的子目录记录成 prefix。

    NEED_WORK_TREE：这个命令需要工作区，不能只在裸仓库里跑。

    也有一些命令不需要仓库，例如 git version；另一些“有仓库就更好”，例如 git config，它们用 RUN_SETUP_GENTLY。这个区别不是装饰，它决定了命令能不能在仓库外运行。

    git add 的两个动作

    阅读 ≈6 分钟 · 检查 ≈4 分钟

    回忆不往回翻：普通 commit 对象里，文件内容本身存在哪里？

    上一节说对象不可变、索引是待提交快照。git add 正好同时碰这两层，但它不写 tree，也不写 commit。

    pretend：git add -n 只报告不落盘，所以不写对象。

    INDEX_WRITE_OBJECT：正常 add 时，index_path 会把 blob 真正写进对象库。

    stat 缓存：把文件的 mtime、size、ino、uid 等记进索引项。下一次 status 先比这些数字，不急着读文件内容。

    所以索引项不是“文件名 → 内容”，而是“路径 → blob 哈希 + 一组 stat 证据 + 模式位”。这组证据是 status 能变快的关键，模块 4 会展开。

    为什么索引是排好序的数组

    内存里的索引是 struct cache_entry **cache：一个按路径字节序排序的指针数组。插入新项时用 memmove 挪出空位，查找时二分。

    read-cache.c:1312 · add_index_entry
    int add_index_entry(struct index_state *istate, struct cache_entry *ce, int option)
{
	int pos;
	...
	ALLOC_GROW(istate->cache, istate->cache_nr + 1,
		   istate->cache_alloc);
	istate->cache_nr++;
	if (istate->cache_nr > pos + 1)
		MOVE_ARRAY(istate->cache + pos + 1,
			   istate->cache + pos,
			   istate->cache_nr - pos - 1);
	set_index_entry(istate, pos, ce);
	istate->cache_changed |= CE_ENTRY_ADDED;
	return 0;
}

    有序带来三件事：按路径二分查找、线性合并两棵树、status 可以顺序扫描工作区。代价是插入要挪数组——这也是超大仓库需要 split index 的原因之一。

    对象库保存不可变的内容，下一次提交必须能通过哈希取到文件字节，所以 add 要先把内容写成 blob。索引保存“这次提交包含哪些路径、每个路径指向哪个 blob、文件当时是什么状态”，提交时才能在不重新扫描工作区的情况下写出 tree。若省略写对象，索引里会指向不存在的 blob；若省略改索引，blob 虽然存在，但没有任何东西告诉 commit 应该把它放进哪棵树。

    模块 2 · 小节 2

    git commit 的收尾

    阅读 ≈6 分钟 · 检查 ≈4 分钟

    回忆commit 写出的根 tree，来自哪里？

    提交时，Git 先确保索引是最新的，再把索引变成 tree，最后写 commit 并移动引用。三个动作对应三个函数，顺序不能换。

    prepare_index 与 cache-tree

    prepare_index 在 builtin/commit.c:351，核心几行是：

    builtin/commit.c:532
    	repo_hold_locked_index(the_repository, &index_lock,
			       LOCK_DIE_ON_ERROR);
	add_remove_files(&partial);
	refresh_index(the_repository->index, REFRESH_QUIET,
		      NULL, NULL, NULL);
	cache_tree_update(the_repository->index, WRITE_TREE_SILENT);
	if (write_locked_index(the_repository->index, &index_lock, 0))
		die(_("unable to write new index file"));

    cache_tree_update 不是“写一棵全新的树”。索引里带着一棵 cache-tree，只有被标记失效的目录才重算。所以提交一个 10 万文件的仓库，通常只为改动路径上的少数目录写 tree。

    关键边界

    对象库只增不改。同一份内容重复提交，tree 与 blob 的哈希相同，不会再写一遍；只有 commit 因为时间/信息/父提交不同而是新对象。

    预测只改提交信息、文件内容不变，新 commit 的根 tree 哈希会怎样？

    写 commit，再移动引用

    commit_tree_extended 把 tree、parents、author/committer 和信息拼成文本，再交给对象库写入。之后 update_head_with_reflog 发起一次引用事务。

    builtin/commit.c:1938
    	if (commit_tree_extended(sb.buf, sb.len,
				 &the_repository->index->cache_tree->oid,
				 parents, &oid, author_ident.buf, NULL,
				 sign_commit, extra)) {
		rollback_index_files();
		die(_("failed to write commit object"));
	}

	if (update_head_with_reflog(current_head, &oid, reflog_msg, &sb,
				    &err)) {
		rollback_index_files();
		die("%s", err.buf);
	}
    the_repository->index->cache_tree->oid

    根 tree：提交用的不是“重新算一遍的树”，而是索引 cache-tree 顶端的 OID。

    update_head_with_reflog(current_head, &oid, ...)

    移动 HEAD：把 HEAD 从旧提交更新到新提交，同时把这次移动写进 reflog。HEAD 是符号引用，真正被改写的是它指向的分支。

    所以“提交成功”的原子性边界在引用更新：commit 对象可能已经写进对象库，但引用事务失败时，你会看到一个没有分支指向的提交——它会在 reflog 或 fsck 里出现。实验 3 会利用这一点。

    用自己的话解释

    ≈2 分钟 · 本地保存
    0 字
    参考答案

    提交先把索引 refresh 并锁住，用 cache-tree 把变化的目录写成 tree，再用这些 tree、父提交和提交信息写出 commit 对象，最后通过引用事务把 HEAD（实际是它指向的分支）移到新哈希并追加 reflog。前三步只写对象库，最后一步才改变“当前分支是什么”。如果引用事务失败，commit 对象已经落盘但没有引用指向它，于是成为孤立对象；它仍能被 fsck 找到，也可能还能从 reflog 里看到。

    本小节可以带走

    • commit 对象由 tree、parents、作者、信息拼成，写入前先算哈希。
    • 引用更新是最后一步；对象与引用之间有一个可观测的缝隙。

    三层加速

    • stat 缓存：最常见的路径，只比元数据，不读内容。

    对象层是只增不改的，真正让历史“活”起来的是引用：分支、HEAD、reflog。它们决定哪些对象算“还在”，也决定了 gc 能删什么、你能找回什么。

    引用就是一个文件

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    回忆普通状态下，.git/HEAD 的内容是什么？

    打开 .git/refs/heads/main，你会看到 40 个十六进制字符加一个换行。没有 JSON，没有数据库。HEAD 稍特殊：它通常写着 ref: refs/heads/main，是一个符号引用。

    引用多到一定程度后，逐个文件会很碎，于是 Git 会把它们打包进 .git/packed-refs。松散引用仍然优先；更新一个已打包的引用时，Git 会写一个松散文件覆盖它。

    可达性与找回

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    回忆gc 决定一个对象能不能删，主要看什么？

    对象库不关心“历史”，它只存对象。是引用把某些提交标成“仍然可达”，gc 再从这些根出发，标记所有能走到的对象；走不到的就是垃圾。但垃圾不一定立刻删——reflog、索引、其他引用都可能是根。

    可达性不是“存在时间”，也不是“有没有被 push”。一个提交可以很旧但被标签引用；也可以很新但没有任何根指向它。

    预测reflog 已过期，又执行了 git gc --prune=now。还能用 fsck 找回那个提交吗？

    误删之后，为什么还能找回来

    三种常见证据源，按可靠性排序：

    1. reflog：HEAD 与各分支的移动记录，包含旧值、新值、动作和时间。
    2. fsck：扫描对象库，报告 dangling / unreachable 的 commit、tree、blob。
    3. 索引与工作区：即使提交没了，暂存区仍可能指向 blob。

    注意 git fsck --lost-found 会把找到的对象写进 .git/lost-found/，但这只是方便你查看，不是恢复引用本身。真正让它“回来”的动作是新建一个引用（分支、标签），让对象重新可达。

    另外，git gc 默认会保留两周内的不可达对象（gc.pruneExpire），并尊重 reflog。很多“删了还能救”的窗口来自这些默认值，而不是 Git 有回收站。

    pack 内部

    阅读 ≈6 分钟 · 检查 ≈4 分钟

    回忆pack 旁边哪个文件提供“哈希 → 偏移”的查找？

    pack 的对象记录不是定长结构。每个对象开头是一个变长头：最高位表示“还有后续字节”，接着 3 位是类型，最低 4 位是 size 的低 4 位；后续每字节再贡献 7 位 size。

    idx 与 bitmap

    .idx v2 的开头是魔法 \377tOc 和版本号，然后是 256 项 fanout：第 i 项表示“首字节 ≤ i 的对象有多少个”。二分时先用首字节定位区间，再在区间内查 OID 表。

        fanout[i] = number of objects whose first byte is <= i

    CRC32: N * 4 bytes
    offsets: N * 4 bytes

    pack checksum: hash_size
    idx checksum: hash_size

    前缀计数：fanout[0x8d] - fanout[0x8c] 就是首字节为 0x8d 的对象数量；两个相邻项直接给出二分区间。

    .bitmap 是另一份可选文件：为某些提交预计算“可达对象集合”的位图。它让 fetch/push 在判断“对方已经有哪些对象”时不必逐个走图，是大型仓库传输提速的关键之一。

    clone 与 fetch

    阅读 ≈6 分钟 · 检查 ≈4 分钟

    回忆fetch 协商的核心是哪一对消息？

    传输的本质是两句话：“我有哪些引用”和“我要哪些对象”。客户端先拿到对方的引用列表，再说“我要这些 tip，但我已经有这些”，服务器据此算出差集并生成一个 pack。

    协议 v2 改了什么

    v2 把“引用广告”和“取对象”拆成两个命令：ls-refs 与 fetch。客户端可以先问引用，再决定要什么；服务器也能按 prefix 过滤引用，减少大仓库的广告体积。

    传输层还有一层常被忽略的选择：file://、ssh、https 都只是“怎么搬字节”，pack 的生成与校验仍在两端各自完成。

    按依赖顺序：index-format.txt → pack-format.txt → pack-protocol.txt → commit-graph.txt。每读一份，回到本课程对应的模块，把图上的一个盒子替换成文档里的字段。
